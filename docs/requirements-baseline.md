# ClipWeaver 原始需求基线

> 来源：`Go 全栈笔试题 2026-09-21.pdf`  
> 性质：本项目最高优先级的产品与验收边界。  
> 适用范围：v0.1 全部设计、任务、实现、测试、Docker 交付与 README。

## 1. 权威顺序与变更规则

文档权威顺序固定为：

```text
原始笔试题
  ↓
requirements-baseline.md
  ↓
technical-design.md
  ↓
tasks/*.md
  ↓
实现代码 / 测试 / README
```

约束：

1. 技术设计可以把原始要求具体化或采用更严格的验收标准，但不得降低、删除或绕过原始要求。
2. 任务卡只能拆解需求，不得改变需求含义。
3. 实现与本文冲突时，以本文为准，当前任务必须进入 `BLOCKED`，先修正文档或实现后再继续。
4. 原题未明确的细节允许作合理假设，但假设必须记录在技术设计或 README，且不能扩大必做范围或削弱验收条件。
5. 任何新增功能都不能影响基础无字幕流程；原题明确不要求的能力不得成为 v0.1 完成条件。
6. 自动字幕当前不在 v0.1 范围内。若后续决定实现，必须先由人工明确调整范围，并同时满足本文“可选字幕”全部约束。
7. 所有任务开始前必须阅读本文；任务标记 `PASS` 时必须确认没有违反本文对应条款。

## 2. 核心目标

### REQ-GOAL-001 本地 Web 完整流程

必须提供一个本地运行的 Web 应用，用户能够：

```text
上传视频素材与口播音频
→ 选择参与混剪的视频
→ 发起混剪
→ 页面预览成片
→ 下载成片
```

验收不能停留在库、命令行工具或单元测试层。

对应：TASK-004、TASK-006、TASK-007、TASK-008、TASK-010。

### REQ-GOAL-002 独立完整交付

交付版本必须经过实际验证，并能够按照 README 从源码构建和使用。允许使用 AI 生成全部代码、测试和文档，但 AI 不能替代实际运行验证。

对应：TASK-009、TASK-010、TASK-011。

### REQ-GOAL-003 自备环境、素材、依赖与合理假设

开发环境、测试素材和依赖由本项目自行准备，不依赖验收方额外提供未声明资源。

原题没有明确的实现细节可以作合理假设，但必须在技术设计或 README 简述；如果某个问题会改变核心功能语义或交付范围，必须先进入 `BLOCKED` 并由人工确认，不能由实现 Agent 自行扩大或缩减范围。

对应：TASK-001、TASK-010、TASK-011。

## 3. 技术约束

### REQ-TECH-001 后端

原题优先 Go + Fiber，也允许 Python 或其他 Web 框架。

ClipWeaver v0.1 冻结为：

- Go
- Fiber

除非人工明确修改技术设计，否则开发任务不得切换后端技术栈。

### REQ-TECH-002 前端

原题优先 React + TypeScript + Ant Design，也允许 Vue + TypeScript 或其他 UI 库。

ClipWeaver v0.1 冻结为：

- React
- TypeScript
- Ant Design

除非人工明确修改技术设计，否则开发任务不得切换前端技术栈。

### REQ-TECH-003 媒体与交付

必须：

- 使用本地 FFmpeg 处理视频；
- 使用 Docker 与 Docker Compose 交付。

不得把核心混剪依赖替换为浏览器端转码或远程媒体处理服务。

### REQ-TECH-004 存储

原题不强制数据库，存储方案可自行选择。

ClipWeaver v0.1 冻结为本地文件系统 + JSON manifest，不引入数据库。

## 4. 必做功能

### REQ-FUNC-001 上传多个视频与一段口播

必须支持上传多个视频素材。

每次混剪请求必须且只能选择一段口播音频。服务端可以保留历史 audio asset，但单次 MixRequest 只能有一个 `audioId`，前端同时只能有一个当前 `selectedAudioId`。

对应：TASK-004、TASK-006、TASK-007。

### REQ-FUNC-002 素材信息与选择

页面必须展示：

- 素材名称；
- 时长；
- 上传/校验状态。

用户必须能够选择哪些视频参与本次混剪。

对应：TASK-004、TASK-007。

### REQ-FUNC-003 无效媒体错误

无效视频或音频不得被静默接受，必须向用户提供清楚、有意义的错误提示。

对应：TASK-003、TASK-004、TASK-007。

### REQ-FUNC-004 随机切片与不重叠

从用户选中的视频中取切片，并随机排列拼接。

必须同时满足：

- 同一视频允许在一次混剪中使用多个不同切片；
- 同一次制作中，同一视频被使用的时间区间不得重叠；
- 切片策略允许自行选择，固定时长分片符合原题。

ClipWeaver v0.1 采用固定 3 秒候选分片 + seeded shuffle。

对应：TASK-002。

### REQ-FUNC-005 目标时长、末片截短与素材不足

必须以口播的实际媒体时长作为成片目标时长。

必须满足：

- 最后一个视频切片允许截短；
- 所选视频可用切片总时长不足时必须明确报错；
- 不得循环、重复使用已经消费的素材区间来补足目标时长。

对应：TASK-002、TASK-006。

### REQ-FUNC-006 输出规格

成片必须为：

- 1080 × 1920；
- 竖屏；
- MP4；
- 保持输入画面原比例；
- 画面无法填满竖屏画布时，空白区域使用黑边填充。

对应：TASK-005、TASK-010。

### REQ-FUNC-007 口播替换素材原声与 0.1 秒误差

必须使用上传的口播替换全部素材原声。

考虑编码误差：

- 成片视频时长与口播实际时长差值不得超过 0.1 秒；
- 成片音频时长与口播实际时长差值不得超过 0.1 秒；
- 不得出现明显语音缺尾。

技术设计可以增加更严格的 container / A-V 对齐断言，但不得放宽以上两条 0.1 秒要求。

对应：TASK-005、TASK-010。

### REQ-FUNC-008 播放、下载、失败与重新制作

混剪成功后必须能够：

- 在页面播放成片；
- 下载成片。

混剪失败时必须：

- 展示有意义的失败原因；
- 允许用户重新制作，不要求重新上传全部素材。

对应：TASK-006、TASK-008。

### REQ-FUNC-009 短素材同步处理

原题按短素材设计：

- 允许同步处理；
- 不要求任务队列。

ClipWeaver v0.1 使用同步 `POST /api/mixes`，不得为了 v0.1 引入任务管理系统、消息队列或后台 Worker 作为必需基础设施。

对应：TASK-006。

## 5. 可选功能：自动字幕

### REQ-OPT-001 v0.1 选择

自动字幕不是基础必做项，不实现不得影响基础要求完成。

ClipWeaver v0.1 决定不实现自动字幕，并必须在最终 README 明确写明“未实现”及验证状态。

### REQ-OPT-002 若未来启用字幕

只有在人工明确把字幕加入范围后，才允许实现。届时必须同时满足：

1. 用户可以开启或关闭字幕；
2. 开启时根据口播自动识别；
3. 自动生成时间轴；
4. 烧录中文字幕；
5. 内容与时间和语音基本对应；
6. 不要求用户额外提供文案或字幕文件；
7. 关闭时成片不添加字幕；
8. 识别失败必须明确报错，不能静默生成无字幕成片并报告成功；
9. 优先使用本地识别，并提供可复现的模型/依赖安装方式，且能在 Docker 中运行；
10. 若使用外部服务，必须说明原因，密钥仅通过环境变量配置，不得提交；
11. 没有外部服务密钥时，基础无字幕混剪流程仍必须可用。

自动字幕不得以任何形式阻塞或削弱基础无字幕流程。

## 6. 源码与自动化测试交付

### REQ-DELIVERY-001 完整源码

必须提交完整前端、后端源码及运行、测试所需文件。

可通过 GitHub 仓库或 ZIP 交付。

### REQ-DELIVERY-002 核心混剪规则自动化测试

核心混剪规则必须有自动化测试，至少覆盖：

1. 切片不重复/同一视频使用区间不重叠；
2. 最后一个切片截短；
3. 规划总时长等于目标口播时长；
4. 素材不足时失败，不循环补足；
5. 随机逻辑支持 seed 或等价的可复现机制。

另外，因原题明确允许同一视频使用多个不同切片，测试必须包含“同一 AssetID 在一个 MixPlan 中贡献多个不重叠 clip”的正向用例。

对应：TASK-002。

## 7. Docker 交付

### REQ-DELIVERY-003 必备 Docker 文件

最终源码必须包含：

- `Dockerfile`
- `.dockerignore`
- Docker Compose 配置

对应：TASK-001、TASK-009。

### REQ-ACCEPT-001 验收机环境

最终验收环境只安装：

- Docker
- Docker Compose

必须能够从源码执行：

```text
docker compose up --build -d
```

并成功构建、启动应用。

不得要求验收机额外安装：

- Go
- Node
- pnpm/npm/yarn
- FFmpeg/FFprobe
- 数据库客户端
- curl/bash 等其他宿主依赖

如测试需要这些工具，必须由 Docker builder/runtime 提供。

对应：TASK-001、TASK-009、TASK-010、TASK-011。

### REQ-ACCEPT-002 首次构建与初始化

首次 Docker 构建允许联网下载依赖。

所有必需配置、环境变量和初始化步骤必须在 README 明确说明。不得依赖开发者本机上预先存在但 README 未说明的状态。

对应：TASK-009、TASK-011。

## 9. 演示材料

### REQ-DELIVERY-005 素材与真实成片

最终必须提供：

1. 自制、允许公开分发的短素材，或可复现生成这些素材的脚本；
2. 使用最终版本实际生成的无字幕成片。

无字幕成片可以：

- 随源码提供，例如明确的 `demo/` 交付目录；或
- 在 README 提供可访问的下载链接。

示例成片必须来自最终实现，不能用手工伪造或仅提供预期截图。

若未来实现字幕，还需另外提供真实中文口播及实际带字幕成片。

对应：TASK-010、TASK-011。

## 10. AI 协作记录

### REQ-DELIVERY-006 AI-NOTES.md

最终必须提供简短的 `AI-NOTES.md`，记录 2～3 个真实发生的关键决策或纠偏案例。

至少能够回答：

- 方案主要由本人提出、AI 提出，还是共同迭代；
- 接受、调整或否决了什么建议；
- 判断依据和取舍是什么；
- 如何发现问题并验证结果。

每个案例应尽量附可核验依据，例如：

- Git commit；
- 测试名称；
- 简短日志；
- 必要的关键对话节选。

不要求：

- 完整聊天记录；
- 完整提示词全文；
- AI 内部推理过程。

不得为了满足文档要求编造错误、否决或纠偏；如果开发过程中没有明显错误，可以如实记录方案被接受以及如何确认其正确。

对应：TASK-011。

## 11. 明确不要求的能力

### REQ-SCOPE-001 v0.1 不得把以下能力变成完成前置条件

原题明确不要求：

- 登录；
- 任务管理系统；
- 转场；
- 字幕编辑；
- 专业时间线；
- 云存储；
- 高并发；
- 线上部署。

ClipWeaver 额外选择不引入：

- 数据库；
- Redis；
- 消息队列；
- 多租户；
- 自动字幕。

实现 Agent 不得因为“工程完整性”自行增加这些能力或依赖。

## 12. 最终验收方式

### REQ-ACCEPT-003 README 驱动、无现场修改

验收按最终 README 从源码构建，并使用短素材验证：

- 功能流程；
- 成片结果；
- 失败反馈。

交付应当在提交前已经完成实际验证，不依赖验收现场临时修改代码、配置或脚本才能通过。

对应：TASK-010、TASK-011。

### REQ-ACCEPT-004 完整流程不可替代

以下内容都不能单独替代完整可运行流程：

- 示例成片；
- Planner 单元测试；
- FFmpeg 集成测试；
- API 测试。

最终必须实际验证：

```text
从源码 Docker 构建
→ 启动
→ 上传视频
→ 上传一段口播
→ 选择视频
→ 发起混剪
→ 生成成片
→ 页面可播放
→ 下载
→ 验证成片媒体规格
→ 验证至少一个失败分支
```

对应：TASK-010、TASK-011。

## 14. 开发启动闸门

任何任务开始前检查：

- [ ] 已阅读本需求基线。

- [ ] 当前任务没有新增原题明确不要求的必需基础设施。

- [ ] 对应原始需求已有自动化或可重复的验收证据。

- [ ] 没有通过增加未要求能力来绕开基础要求。
